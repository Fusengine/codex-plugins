# GitHub Actions Security (pipeline author's view)

**Load when:** a workflow touches secrets, deploys, uses third-party actions, or runs on self-hosted runners. This is how to write safe workflows; auditing an existing repo's supply chain belongs to `dependency-audit` / `security-expert`.

## 1. `permissions`: least privilege

- Set the default to read-only for repository contents (`permissions: {}` or `contents: read` at workflow level), then raise per job. Any user with write access to the repo can read all repository secrets, so credentials used in workflows must be minimal.
- Common job-level grants: `contents: write` (create release), `packages: write` (GHCR), `id-token: write` (mint OIDC token, nothing else), `attestations: write` + `artifact-metadata: write` (build attestations), `pull-requests: write`.
- Without `id-token: write` the OIDC JWT cannot be requested.
- Reusable workflow: the callee's `GITHUB_TOKEN` permissions can be kept or reduced by the caller, not raised (see [Not verified](#not-verified)).

## 2. Third-party actions: pin them

Order of preference:
1. **Workflow dependency lockfile** (`.github/workflows/actions.lock`, generated by the `gh actions-lock` CLI extension, never hand-edited): pins every action including transitive ones, records owner/repo IDs, GitHub states it supersedes SHA pinning for repos that adopt it. It does not pin reusable workflow calls (`jobs.<id>.uses`) - pin those by full SHA.
2. **Full-length commit SHA** with the tag in a trailing comment (as in all templates here). Verify the SHA belongs to the action's own repo, not a fork.
3. Tag only for actions you trust (verified creator), accepting that tags can be moved.

Org policy "Require actions to be pinned to a full-length commit SHA" exists; a lockfile satisfies it for onboarded workflows. Let Dependabot raise the SHA bumps. Audit the source of any action that handles secrets.

## 3. OIDC instead of stored credentials

The job asks GitHub's OIDC provider (`https://token.actions.githubusercontent.com`) for a JWT; the target system validates the claims and returns a short-lived credential valid for the job.

- Needs `permissions: id-token: write`. Request: `curl -H "Authorization: bearer $ACTIONS_ID_TOKEN_REQUEST_TOKEN" "$ACTIONS_ID_TOKEN_REQUEST_URL&audience=<aud>"` (JSON field `value`). Default `aud` is the repository owner URL; set your own audience per consumer.
- The trust rule on the target side must bind **claims**, not just "any GitHub token": `sub` (for example `repo:<org>/<repo>:environment:production`), `repository`, `ref`, `job_workflow_ref`, `environment`. A role that trusts only the issuer lets every repository on GitHub in.
- Repositories created after 2026-07-15 use an immutable `sub` format that includes owner and repository IDs; read the OIDC reference before copying an old `sub` string.
- Self-hosted fit: OpenBao/Vault JWT auth (`POST /v1/auth/jwt/login` with `{"jwt","role"}`, token in `auth.client_token`), see [templates/github-oidc-deploy.yml](templates/github-oidc-deploy.yml) and `devops-secrets`.
- Mask every derived value (`::add-mask::`); register generated secrets; never pass structured JSON/YAML as one secret (redaction needs exact matches).

## 4. Script injection

`${{ ... }}` is substituted into the script text before the shell runs. Never inline untrusted fields (`github.event.pull_request.title`, branch names, issue bodies, `inputs.*`) in `run:`.

```yaml
- env:
    TITLE: ${{ github.event.pull_request.title }}
  run: ./check.sh "$TITLE"        # value stays data, quoted
```

Or pass it as an input to an action. Quote shell variables.

## 5. Privileged triggers

`pull_request_target` and `workflow_run` run with secrets and write token in the base context. Combined with a checkout of the PR head they hand your secrets to the PR author. Rule: never check out or execute PR code in these; use plain `pull_request` for tests. Also keep `persist-credentials: false` on `actions/checkout` unless the job pushes.

## 6. Self-hosted runners

- Persistent self-hosted runners do not give a clean instance per job: a prior job's files, credentials and processes remain. **Do not use self-hosted runners on public repositories** (anyone can open a PR); be cautious on private ones.
- Prefer **ephemeral** runners (one job, then gone; GitHub assigns only one job to such a runner) with automated provisioning, or the runner-scale-set / Kubernetes controller; GitHub recommends autoscaling with ephemeral runners only, and forwarding runner logs off-host.
- Isolate by trust: separate runner groups for production-deploy jobs; no shared Docker socket; no long-lived credentials on the host; network egress filtered; the host patched (you own OS updates; only the runner application updates itself).
- Registering/removing runners: see [destructive-pipeline-actions.md](destructive-pipeline-actions.md).

## 7. Checklist

`permissions` set at top and per job; actions pinned (lockfile or SHA); no `${{ }}` of untrusted data in `run`; OIDC claims bound to repo+environment; deploy jobs behind an environment with reviewers; `timeout-minutes` everywhere; no secrets in caches or artifacts; runners ephemeral or private-only.
