# Destructive Secret Operations

**Load when:** a command in the table below is on the table, or any command whose failure would lose, expose or invalidate secret material or a key.

## Rule

The agent **proposes**, never runs on its own initiative. A proposal is one block per command:

```
ACTION:      <exact command, tool, target cluster/context/namespace/path>
EFFECT:      <what changes, and plainly what becomes UNRECOVERABLE>
PROOF:       <read-only evidence gathered first: backup taken and restore tested, dependants listed, quorum, versions>
WAIT-FOR-GO: yes - run only after the user names the object (path, mount, namespace, secret, repo, key fingerprint)
```

Also always: never print or paste a secret value; never place one on a command line; take and verify a backup or snapshot first; one go covers one block; stop and report if a precondition fails.

## Vault / OpenBao (`vault`; `bao` for OpenBao)

| Command | Exact effect (docs read) | Unrecoverable | PROOF before proposing |
|---------|--------------------------|---------------|------------------------|
| `vault operator rekey -init ...` then unseal keys | Generates a new set of unseal keys / share count / threshold; zero downtime; needs a quorum of **current** keys; with auto-unseal use `-target=recovery`; `-verify` + nonce adds a verification phase; `-backup` stores PGP-encrypted keys in Vault core (`-backup-retrieve`, `-backup-delete`) | Old shares stop working once complete; shares not delivered/recorded are lost forever | Custodians present, secure channel for new shares, rekey `-status`, snapshot taken, verification option chosen |
| `vault operator seal` | Discards the in-memory root key; the server answers nothing but unseal/status; resets an unseal in progress | Not data, but a **full outage** until unsealed; with lost shares it is permanent | Shares/seal mechanism confirmed available and tested, impact on consumers listed, reason (intrusion/maintenance) stated |
| `vault secrets disable <path>/` | **All secrets generated by the engine are immediately revoked** and its Vault data removed; heavy load on large mounts | Engine data and issued dynamic credentials (and dependants of KV data) | Mount inventory, snapshot, consumers listed; for failed revocation the docs describe a force path via `vault lease revoke -force -prefix <mount>`, which can leave dangling credentials |
| `vault kv destroy -mount=<m> -versions=<n> <key>` | Permanently removes the named versions' data | Those versions | `vault kv metadata get` shows versions; need confirmed; soft `delete` is the reversible alternative |
| `vault kv metadata delete -mount=<m> <key>` | Deletes **all versions and metadata** of the key | Entire history of the key | Same, plus dependants (ESO `find` relies on metadata) |
| `vault lease revoke <id>` | Revokes one lease, invalidating the underlying credential | The credential | Lease lookup, owner of the consumer |
| `vault lease revoke -prefix <path>` | Revokes **every** lease under the prefix; `-force` removes the lease even if the engine fails to revoke (Vault and the target can desync); `-sync` waits | All credentials under the prefix at once (mass outage of consumers) | List of leases/consumers, window, rollback plan (re-issue) |
| `vault token revoke ...` (bulk) / auth `disable` | Invalidates tokens and their children; `vault auth disable <path>/` removes the method and its tokens | The tokens/logins | Not re-read here: read the command page, list dependants |
| `vault write -force database/rotate-root/<name>` | Rotates the DB root user; the old root password is no longer accessible | The old root password | A **dedicated** Vault DB user is in use; recovery path (DBA) exists |
| `vault operator raft snapshot restore -force <file>` | Replaces cluster state with the snapshot (force needed when keys do not match); returns before completion; wait for "post-unseal setup complete" and "vault is unsealed" | Everything written after the snapshot; leases/tokens issued later | Snapshot age, its unseal keys/seal accessible, restore tested on a scratch cluster, writers stopped |
| `vault operator raft remove-peer <id>` | Removes a node from the raft cluster | Node membership (the node must rejoin/rebuild) | `list-peers`, quorum math |
| Deleting the auto-unseal KMS key / transit key | Cluster **cannot be recovered, even from backups** (Vault docs) | The whole cluster's data | Never propose without migrating the seal first |
| Disabling an audit device | Stops writing; hashing of old entries impossible later | Audit continuity | At least one other device remains enabled |

## SOPS / age

| Command | Effect | Unrecoverable | PROOF |
|---------|--------|---------------|-------|
| `sops updatekeys <file>` (many files) / `sops rotate -i --rm-age <pub> <file>` | Re-encrypts data keys to a new recipient set; rewrites files in place | If **no remaining recipient identity** is available, the file is permanently unreadable | At least two recipients incl. an offline recovery one; `git status` clean first; decrypt test (to `/dev/null`) with a remaining identity |
| Deleting/overwriting the age identity file | Loses the ability to decrypt everything encrypted only to it | All files whose only recipient it was | Another recipient exists; offline copy tested |
| Removing a recipient from `.sops.yaml` | No effect on old ciphertext | Nothing is revoked: rotate underlying secrets | n/a |

## Sealed Secrets

| Command | Effect | Unrecoverable | PROOF |
|---------|--------|---------------|-------|
| `kubectl delete secret -n kube-system -l sealedsecrets.bitnami.com/sealed-secrets-key` (or any single key Secret) | Removes the controller's sealing private key(s) | Every SealedSecret sealed to those keys becomes undecryptable; re-create each secret value at its source and re-seal | Encrypted offline backup made **after the last renewal** and restore tested on a scratch cluster |
| Restore: `kubectl apply -f <backup>` then restart controller pod | Replaces keys | Newer keys not in the backup | Compare key Secret names before/after |
| Disabling renewal (`--key-renew-period=0`) | One key forever | Increases blast radius of a key leak | Owner decision |

## Kubernetes

| Command | Effect | Unrecoverable | PROOF |
|---------|--------|---------------|-------|
| `kubectl delete secret <name>` | Deletes the Secret object (in use by running pods: they continue until restart, then fail) | The value if it was only in the cluster (not regenerated by ESO/SealedSecret) | Source of truth exists (store/Git), consumers listed (`kubectl get pods -o jsonpath` on secret refs, no values) |
| Delete an `ExternalSecret`/`SealedSecret` with `creationPolicy: Owner`/ownership | Garbage-collects the generated Secret | Same | Same |
| Change EncryptionConfiguration provider order, remove a key, or drop a provider | Resources encrypted with a removed key/provider become unreadable via the API | Those resources, unless the old key is restored | New key backed up; all apiservers restarted in the documented order; all Secrets rewritten before removing the old key |
| `kubectl get secrets -A -o json \| kubectl replace -f -` | Rewrites every Secret (re-encryption); retry on conflicts | Rewrites with a stale read can overwrite concurrent writes (conflicts are retried) | Admin context named, maintenance window, etcd snapshot (`devops-k8s-cluster`) |
| `kubectl delete namespace` | Removes all Secrets inside | Values not stored elsewhere | See devops-kubernetes kubectl-safe-ops |

## Git history rewrite (leak cleanup)

| Command | Effect | Unrecoverable | PROOF |
|---------|--------|---------------|-------|
| `git filter-repo ...` / BFG + `git push --force` | Rewrites commit IDs; every clone, open PR and fork diverges | Original history on the remote; other people's unpushed work if they force-sync | **Credential already revoked and rotated**; full backup mirror clone; collaborators warned; branch protection plan; owner's explicit go (force-push is owner-gated) |

History rewrite never replaces revocation ([leak-prevention-response.md](leak-prevention-response.md)).
