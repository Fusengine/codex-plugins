# Secrets Lifecycle and Tool Choice

**Load when:** a new secret appears, a tool must be chosen, or the agent is about to run any command that could echo a secret.

## Agent output rules (apply before every command)

| Rule | Concretely |
|------|-----------|
| Never print a value | No `cat` of a key file, no `sops -d` to stdout, no `kubectl get secret -o yaml`, no `base64 -d`, no `vault read database/creds/...` in the chat. Show keys, paths, versions, lease IDs, fingerprints |
| Never place a value in an argument | Arguments reach shell history, `ps` and CI logs. Use a file (mode 0600), stdin, a prompt or the store's own injection. `vault kv put -h` shows the file and stdin forms (flags not re-verified here) |
| Redact before quoting | Replace values with `<REDACTED>` in any manifest, event, log or diff you cite |
| Check presence, not content | `jq 'keys'`, `vault kv metadata get`, `kubectl get externalsecret`, lease lookup |
| Generated secrets stay on the host that needs them | Generate with the store or a key tool (for example `age-keygen -o <file>`) and keep the output in a 0600 file or the store itself |
| Examples use placeholders | `<REDACTED>`, `CHANGE_ME`, `<AGE_RECIPIENT>`; never a realistic key shape |

## Taxonomy

| Class | Examples | Lifetime target | Preferred delivery |
|-------|----------|-----------------|--------------------|
| Human credentials | SSO, admin passwords, break-glass | Per person | Identity provider, MFA; never shared |
| Service credentials (static) | Database password, API token | Rotate on a schedule | Store + sync (ESO) or SOPS in Git |
| Service credentials (dynamic) | Vault database role, cloud STS | Minutes to hours | Vault/OpenBao engine with leases |
| Workload identity | ServiceAccount token, OIDC token | Minutes | Projected token + auth method; no stored secret |
| Cryptographic keys | age identity, KMS key, SSH CA key, TLS private key | Long, with a documented rotation | Offline custody, HSM or KMS where available |
| Certificates | Server/client X.509 | Short with automated renewal | PKI engine or ACME (devops-networking) |
| Seal/recovery material | Vault unseal keys, recovery keys, root token | Until rekey | Split among custodians, offline |

## Lifecycle

1. **Create** - generated by the store or a tool, never typed from memory; entropy from the tool.
2. **Distribute** - pull by identity (ServiceAccount, OIDC) rather than push by person; one consumer, one credential.
3. **Rotate** - on schedule and on any suspicion; the consumer must survive the change (dual-credential overlap or reload). See [rotation-lifecycle.md](rotation-lifecycle.md).
4. **Revoke** - leases, tokens, sessions and the credential itself at the system that honours it; proof by a failed login with the old value (done by a test client, never by pasting the value).
5. **Audit** - who read what and when: Vault/OpenBao audit devices, Kubernetes API audit, Git history for encrypted files.

## Tool choice by context

| Context | Choice | Notes |
|---------|--------|-------|
| One cluster or host, Git is the source of truth, team under ~10 | SOPS + age ([sops-age.md](sops-age.md)) | How Flux or Argo CD decrypt SOPS files is in devops-gitops-packaging |
| Kubernetes only, developers must not read secrets back | Sealed Secrets ([sealed-secrets.md](sealed-secrets.md)) | Ciphertext is cluster-bound; controller key custody is the risk |
| Many consumers, rotation, per-request credentials, audit | Vault or OpenBao + ESO ([vault-openbao-core.md](vault-openbao-core.md), [external-secrets-operator.md](external-secrets-operator.md)) | You now operate a tier-0 service: backup, seal, HA |
| Licence matters (internal use vs offering a competing product) | Read the Vault BUSL 1.1 terms vs OpenBao | See vault-openbao-core.md; legal review is not the agent's call |
| Public cloud secret manager already authoritative | ESO provider for it | Out of scope beyond this line; cloud IAM is not covered here |
| Ansible-only automation | Ansible Vault or SOPS | Pointer: devops-ansible |
| Build-time | BuildKit secret mounts | Pointer: devops-docker |

## Bootstrap problem

Every secret system needs one first secret: the SOPS age identity, the Sealed Secrets controller key, the Vault unseal/recovery keys or root token, the ESO store credential. Rules:

1. Name the bootstrap secret for each system and where its offline copy lives.
2. Keep that copy outside the system it unlocks (a Vault cluster cannot hold its own unseal keys; a cluster cannot hold the only copy of the key that decrypts its own GitOps secrets).
3. Prefer identity over a stored bootstrap secret: Kubernetes auth for ESO, auto-unseal via a separate KMS/transit Vault, OIDC for CI.
4. Test recovery from the offline copy before relying on it ([destructive-secret-ops.md](destructive-secret-ops.md) for restore commands).
