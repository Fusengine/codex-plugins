# Version Skew, Upgrades, Certificates

**Load when:** any version change or certificate question. Checklist template: [cluster-upgrade-checklist.md](templates/cluster-upgrade-checklist.md).

## Skew limits (newest kube-apiserver = 1.37 in the examples)

| Component | Rule |
|-----------|------|
| kube-apiserver (HA) | Newest and oldest instance within **one** minor |
| kubelet | Not newer than the apiserver; up to **three** minors older (1.37 -> 1.37..1.34) |
| kube-proxy | Not newer than the apiserver; up to three minors older; within three minors of the kubelet beside it |
| controller-manager, scheduler, cloud-controller-manager | Not newer than the apiserver they talk to; same minor or one older |
| kubectl | Within one minor of the apiserver, older or newer |

During a mixed HA upgrade the narrower limits apply: with apiservers at 1.37 and 1.36, kubelets must be 1.36..1.34 and controller-manager/scheduler 1.36. A kubelet that stays three minors behind blocks the next control-plane upgrade. Maintained minors today: 1.37, 1.36, 1.35 (1.34 ended 2026-10-27).

## Upgrade order (never skip a minor, even with one control-plane node)

1. Control-plane apiserver(s) -> 2. controller-manager, scheduler, cloud-controller-manager -> 3. kubelet and kube-proxy on every node. Prefer to be on the latest patch of the current minor first, then upgrade to the latest patch of the target. Admission webhooks must handle the new API versions (use `matchPolicy: Equivalent`).

## kubeadm procedure (https://kubernetes.io/docs/tasks/administer-cluster/kubeadm/kubeadm-upgrade/)

Before: read the release notes; fresh etcd snapshot ([etcd-backup-restore.md](etcd-backup-restore.md)); swap off; backups of app state. Control-plane nodes **one at a time**.

```bash
# first control-plane node
sudo apt-mark unhold kubeadm && sudo apt-get update && sudo apt-get install -y kubeadm='1.37.x-*' && sudo apt-mark hold kubeadm
kubeadm version ; sudo kubeadm upgrade plan
sudo kubeadm upgrade apply v1.37.x                  # other control-plane nodes: sudo kubeadm upgrade node
# every node, after kubeadm: drain (needed for a MINOR kubelet upgrade), then kubelet/kubectl
kubectl drain <node> --ignore-daemonsets
sudo apt-mark unhold kubelet kubectl && sudo apt-get install -y kubelet='1.37.x-*' kubectl='1.37.x-*' && sudo apt-mark hold kubelet kubectl
sudo systemctl daemon-reload && sudo systemctl restart kubelet
kubectl uncordon <node> ; kubectl get nodes
```

Facts to respect: `kubeadm upgrade` renews the certificates it manages (opt out with `--certificate-renewal=false`); all containers restart because the spec hash changes; the CNI provider is upgraded manually (first node, unless it is a DaemonSet-only chart); since 1.28 addons (CoreDNS, kube-proxy) upgrade only after the last control-plane instance; a stalled `kubeadm upgrade` is idempotent - re-run it, or `kubeadm upgrade apply --force` on the same version; backups are written to `/etc/kubernetes/tmp/kubeadm-backup-etcd-*` and `kubeadm-backup-manifests-*` and must be cleaned up by hand. `kubeadm upgrade` cannot reconfigure a cluster. During an etcd upgrade, in-flight apiserver requests stall; the docs suggest `killall -s SIGTERM kube-apiserver; sleep 20` before `kubeadm upgrade`. For RHEL-family hosts use the `dnf` forms with the `kubernetes` repo excludes disabled as shown on the page.

```
ACTION   kubeadm upgrade apply v1.37.x      (control-plane node 1 of 3)
EFFECT   rewrites static pod manifests, restarts apiserver/controller-manager/scheduler and possibly etcd on this node; renews its certificates
QUORUM   etcd keeps 2 of 3 members on the other nodes; do the next node only when this one is Ready and etcd health is green
PROOF    snapshot taken and listed; `kubeadm upgrade plan` output reviewed; skew table checked
WAIT-FOR-GO
```

k3s: servers first one at a time, then agents; the install script does not drain ([k3s-cluster.md](k3s-cluster.md)). Talos: OS and Kubernetes upgrades are separate commands ([talos-cluster.md](talos-cluster.md)).

## Certificates (kubeadm)

Client certificates generated by kubeadm last **1 year** (CAs 10 years). `kubelet.conf` is not listed because the kubelet rotates its own certificates under `/var/lib/kubelet/pki`.

```bash
sudo kubeadm certs check-expiration          # every control-plane node; "EXTERNALLY MANAGED" rows are yours to renew
sudo kubeadm certs renew all                 # or one name (apiserver, ...) - run on EVERY control-plane node
```

Upgrading at least yearly renews everything automatically. After `renew`, restart the control-plane static pods (the new certs are read at start) and refresh the admin kubeconfig you copied to `~/.kube/config`. Only non-CA certificates are renewable by `kubeadm certs renew`; validity can be set with `certificateValidityPeriod` / `caCertificateValidityPeriod` in `ClusterConfiguration`. kubeadm cannot manage certificates signed by an external CA ("External CA" mode when `ca.key` is absent). Alert on expiry in devops-observability (30 days).

## Pitfalls

| Trap | Consequence |
|------|-------------|
| Jumping 1.35 -> 1.37 | Unsupported; API deprecation and storage-version assumptions break |
| Upgrading kubelet before the apiserver | Kubelet newer than apiserver is unsupported |
| Leaving `apt` unheld | `apt upgrade` moves kubelet independently of the plan |
| Certificates expire after a year without upgrades | apiserver/etcd clients fail; control plane unreachable until renewed |
| Forgetting the CNI upgrade step | Old agent against new API/kernel features |

## Verification

`kubectl get nodes` (all `Ready`, versions as planned), `kubectl version`, `kubeadm certs check-expiration` (fresh dates), `kubectl -n kube-system get pods`, then smoke-test the workloads (devops-kubernetes).
