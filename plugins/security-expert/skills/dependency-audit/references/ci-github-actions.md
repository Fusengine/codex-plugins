# GitHub Actions Checks

Reference: GitHub "Secure use reference"
(https://docs.github.com/en/actions/reference/security/secure-use). Standard for findings:
OWASP Top 10:2025 A03 Software Supply Chain Failures. All checks are read-only.

## 1. Third-party actions: lockfile or full commit SHA

GitHub documents a workflow dependency lockfile as the better option than SHA pinning:
`.github/workflows/actions.lock`,
generated by the `gh actions-lock` GitHub CLI extension; it pins every action, including
transitive ones, and supersedes SHA pinning for onboarded workflows
(https://docs.github.com/en/actions/concepts/security/workflow-dependency-lockfiles).
It does not pin reusable workflow calls (`jobs.<job_id>.uses`): those still need a full SHA.

Without a lockfile, every `uses: owner/repo@ref` must use a full-length commit SHA:

```bash
ls .github/workflows/actions.lock 2>/dev/null
rg -n "uses:\s*[^.\s][^@\s]*@" .github/workflows .github/actions 2>/dev/null \
  | rg -v "@[0-9a-f]{40}(\s|$|#)"
```

Each hit (tag or branch ref, no lockfile) → finding. Why tags are not enough: on 2026-03-19 an
attacker force-pushed 76 of 77 version tags of `aquasecurity/trivy-action` to credential-stealing
code; workflows pinned to a SHA predating the action's own pinning of `setup-trivy` were still
exposed through that unpinned transitive action (GHSA-69fq-xp46-6x23 / CVE-2026-33634,
https://github.com/advisories/GHSA-69fq-xp46-6x23).

## 2. Least-privilege `permissions:`

- Every workflow should declare `permissions:` at top level (GitHub recommends read-only
  `contents` by default) and raise scopes per job only where needed.
- No `permissions:` key → the job gets the repository default token scope, which the audit
  cannot see from files alone → "needs manual review" unless the repo setting is confirmed.
- `permissions: write-all` or broad `write` on a job that runs untrusted input → finding.

## 3. `pull_request_target` / `workflow_run` with untrusted code

These triggers run in a privileged context (secrets, write token, shared cache). Finding when
such a workflow checks out pull-request code, e.g. `actions/checkout` with
`ref: ${{ github.event.pull_request.head.sha }}` or `head.ref`, then builds, installs or runs it.

```bash
grep -rlnE "pull_request_target|workflow_run" .github/workflows
```

Open each hit and trace the checkout `ref:` and the steps that follow.

## 4. Expressions interpolated into `run:`

`${{ github.event.* }}` (titles, bodies, branch names, commit messages) expanded inside a
`run:` script is a shell injection. The fix GitHub documents: pass the value through `env:`
and use the shell variable (`"$TITLE"`), or pass it to an action input.

```bash
grep -rnE '\$\{\{\s*github\.event\.' .github/workflows .github/actions
```

Keep only hits located inside a `run:` block (or a script input of an action); those are findings.

## 5. Optional scanners (presence check, never installed)

```bash
command -v zizmor && zizmor --offline --format=json .   # https://docs.zizmor.sh/usage/
command -v actionlint && actionlint -format '{{json .}}' # https://github.com/rhysd/actionlint/blob/main/docs/usage.md
```

- zizmor exit codes 11-14 mean findings (highest severity informational → high); 0 = none.
  `--offline` skips audits needing the GitHub API; with a token it runs online audits.
- **FIX (option only):** `zizmor --fix` (safe fixes) / `--fix=all` rewrite workflow files in place.
- actionlint is a correctness linter that also flags untrusted inputs in scripts; treat its
  output as evidence for checks 1-4, not as findings on its own.
