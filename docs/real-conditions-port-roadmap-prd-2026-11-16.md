## Root causes and doctrine gaps

1. **The hand-written router is the non-PRD-mode doctrine, not a leak.** `plugins/ai-pilot/skills/lead-orchestration/SKILL.md` (bullets before "Harness PRD mode") already makes the coordinator write `<project>/.codex/apex/prd.json` and the task PRD by hand with agents reporting under `.codex/apex/prd/agents/`. So criterion "no `.codex/apex/prd.json`" for R3 was mis-specified: the correct discriminator is "no harness `prd` command and no `prd init`". The router file appearing in R3 and in every project is expected.
2. **`FUSE_PRD` is doctrine-only.** `grep -rn FUSE_PRD` in the installed harness `dist/`, `src/` and README returns nothing; `harness prd status` works with an empty env (verified with `env -i`). The skill says Harness PRD mode "applies only when `FUSE_PRD=1`", but in R3 the `commit` child and a typescript-expert child still used `harness prd status/validate` without it. Nothing technical stops them; the briefs are encrypted in the rollouts so the origin of that instruction is not visible. Gap: either state in the skill that agents must not call `prd` commands when `FUSE_PRD` is unset, or gate the CLI on `FUSE_PRD`.
3. **R2b read-tracker false block.** The APEX SOLID reference gate did not register `cat dir/{a,b,c}.md` as reads of those references, then denied the identical retry (`[REPEAT]`). The gate's hint also listed references under `/Users/brunoazoulay/.claude/plugins/marketplaces/fusengine-plugins/...` (Claude marketplace paths) in a Codex `CODEX_HOME`, in a `env -i` run. This is harness behaviour, not PRD doctrine; it makes a run stall while the lead ends with a "blocked" report. Not fixed (non-goal).
4. **PRD init owner.** In R2/R2c the first `prd init` is run by a typescript-expert child, not by the lead; the skill says "an agent runs `prd init`", so this matches the text. In R2b the lead skipped `prd init` and hand-wrote the router (the lead also edits with `apply_patch` there), diverging from the PRD-mode text.
